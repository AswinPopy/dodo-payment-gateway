# AI Usage

I used Cursor (agent chat) for most of the implementation after I had already built the basic invoice, payment, and idempotency skeleton. I did not use Claude or ChatGPT for the assignment.

## How I used AI

I mainly used Cursor as a coding assistant and to help me work through the different evaluation cases.

* I used Cursor to convert the in-process `MockPSP` into a separate HTTP service under `cmd/mock-psp` running on `:8081`, and to connect it to `internal/psp/http_client.go`.
* I used it to go through the main payment scenarios such as concurrent payments, PSP timeouts, failures, crashes before persistence, idempotency key reuse, and already-paid invoices. I then implemented the changes I agreed with, including the invoice row lock, request hashing, webhook settlement, and the outbound webhook worker.
* I also used Cursor for things like HMAC webhook signing, retry/backoff logic, API key rotation and revocation, Docker Compose setup, startup migrations, and some of the curl commands used during testing.
* I used Cursor autocomplete for smaller pieces of code such as JSON request/response structs and repository `Scan` code.

The core payment state machine and the main design decisions were mine. I also reviewed the changes made to `payment_service.go` rather than treating the generated code as a black box.

## Three decisions I made

### 1. I kept the mock PSP as a separate service

The assignment allowed either a separate service or a route inside the invoice API. I chose a separate `cmd/mock-psp` process running on `:8081`.

I wanted the invoice service to communicate with the PSP through an actual HTTP call. This makes the timeout and network failure cases much more realistic and avoids accidentally sharing memory between the two services.

### 2. I used a row lock for payment concurrency

For concurrent payment requests, I decided to lock the invoice row with `SELECT ... FOR UPDATE`.

The database also has a unique index allowing only one `PENDING` payment attempt per invoice, which I kept as an additional safety check.

I considered advisory locks and serializable transactions, but I felt the row lock was easier to reason about and explain. The important part for me was that the payment start is serialized at the invoice level before creating the attempt and calling the PSP.

### 3. I kept timeout and network errors as `PENDING`

This was one of the decisions I considered most important.

If the PSP times out, we don't actually know whether the payment went through. The PSP might have charged the customer even though our request timed out.

So I did not mark these cases as `FAILED`.

Instead:

```text
PSP timeout / network error
        ↓
Payment attempt = PENDING
Invoice = OPEN
        ↓
Resolve later through webhook/reconciliation
```

A definite PSP response such as `insufficient_funds` or `card_declined` can safely be recorded as `FAILED`.

This avoids allowing a customer to retry and potentially get charged twice.

## Things I ran into while using AI

The AI wasn't always correct, and I had to debug a few things myself.

### 1. Migration issue

After adding automatic migrations, the server failed with:

```text
relation "businesses" already exists
```

The problem was that I had already created the tables manually earlier, while the new migration tracking table was empty. The migration code assumed it was starting with a completely new database.

I fixed this by marking the existing migrations as already applied instead of trying to recreate the tables.

### 2. Some curl commands didn't work as expected

The first test commands generated by Cursor contained shell comments and placeholders such as:

```text
PASTE_BUSINESS_ID
```

Since I was running them directly in zsh, some of the commands didn't behave as expected. I also accidentally used placeholder values in a few requests, which resulted in errors such as `invoice not found`.

I replaced the placeholders with the actual IDs from my database and ran the tests again.

### 3. Reusing an idempotency key

One of the generated examples reused an idempotency key on a different invoice.

Because my implementation hashes the request details and checks them against the existing idempotency key, the API correctly returned:

```text
idempotency key reused with different request
```

At first I thought this meant the already-paid check was broken, but after looking at the request I realized the test itself was wrong. I used a new idempotency key and the flow worked correctly.

## How I verified the implementation

I tested the important payment cases manually:

* `tok_success` → payment became `SUCCEEDED` and the invoice became `PAID`.
* Paying the same invoice again with a new idempotency key → rejected because the invoice was already paid.
* Two concurrent payment requests → only one payment attempt proceeded; the other was rejected because the invoice was already being processed.
* `tok_network_error` → payment remained `PENDING`.
* `tok_timeout` → the request returned after roughly 2 seconds and the payment remained `PENDING` instead of waiting for the PSP's 30-second response.

These tests helped me verify that the important failure and concurrency cases were actually handled by the implementation rather than just being covered in the design.
